# Codex Account Switcher 아키텍처 결정 기록

- 상태: 승인됨
- 기준일: 2026-07-30
- 적용 범위: Spike, Swift core, macOS 메뉴바 MVP
- 관련 문서: `01_product_requirements.md`

## 1. 사용법

이 문서는 합의된 선택뿐 아니라 이유, 기각 대안, 재검토 조건을 보존한다. 새 task는 구현 전에 이 문서와 제품 요구사항을 함께 읽어야 한다.

결정 우선순위:

1. 사용자와의 최종 grilling 합의
2. 이 결정 기록
3. 제품 요구사항
4. 초기 첨부 문서와 외부 참고 구현

초기 첨부의 제안이 아래 결정과 다르면 아래 결정이 우선한다.

## ADR-001: 제품은 편의용 인증 전환기다

- 상태: 승인
- 결정: 하나의 공용 Codex 로컬 상태를 유지하고 계정별 인증만 전환한다. 보안 격리 제품으로 정의하지 않는다.
- 이유:
  - 사용자의 핵심 목적은 개인·회사 계정에서 대화와 작업을 이어 쓰는 것이다.
  - 계정별 전체 환경 분리는 동일 task와 공용 설정 사용 목적에 맞지 않는다.
  - 최소 변경 대상이 `auth.json` 하나라 제품과 검증 범위가 작다.
- 공유 항목: `config.toml`, skills, sessions, history, SQLite, MCP 설정, 기타 `~/.codex` 상태, 공식 앱 로컬 상태
- 분리 항목: 저장 프로필의 인증 비밀
- 기각 대안:
  - 계정별 `CODEX_HOME`: task와 설정이 갈라져 핵심 목표를 훼손한다.
  - 계정별 Electron `user-data-dir`: 공식 앱 실행 구조 의존성과 유지보수 위험이 커진다.
  - VM 또는 macOS 사용자 계정 분리: 격리는 강하지만 전환 편의와 task 연속성이 사라진다.
- 재검토 트리거:
  - 공식 앱이 인증 외 상태에 계정 소유권을 강제해 동일 task 재개가 불가능함
  - 회사 정책이 개인·회사 로컬 상태 공유를 금지함
  - 사용자의 우선순위가 편의에서 격리로 바뀜
- 재검토 시 원칙: 이 제품의 변형으로 억지 확장하지 않고 별도 격리 제품으로 다시 정의한다.

## ADR-002: 별도 ChatGPT 로그인 두 개를 전제로 한다

- 상태: 계정 구분 방식 승인, 계정 수는 ADR-028이 대체
- 결정: 계정 A와 B는 서로 다른 이메일을 가진 별도 ChatGPT 로그인이다. 같은 로그인 안의 workspace 전환은 범위 밖이다.
- 이유:
  - 사용자의 실제 개인·회사 계정 구조가 별도 로그인이다.
  - MVP의 이메일 검증이 두 계정을 명확히 구분한다.
- 기각 대안:
  - 같은 이메일의 workspace 전환 지원: `account/read` 이메일만으로 구분할 수 없고 MVP 복잡도가 커진다.
- 재검토 트리거:
  - 사용자가 같은 로그인 내 여러 workspace 지원을 요구함
  - app-server가 안정적인 `userId`와 `workspaceAccountId` 계약을 공개함

## ADR-003: 동일 task의 양방향 실제 메시지가 제품 성립 조건이다

- 상태: 승인, 제품 중단 gate
- 결정: A에서 비민감 기준 task를 한 번만 만든다. 그 정확히 같은 task ID를 B에서 열고 실제 메시지를 성공시킨 뒤 A로 돌아와 다시 실제 메시지를 성공시키는 왕복을, 새 task를 만들지 않고 3회 연속 통과해야 한다.
- 이유:
  - 사용자가 원하는 것은 인증 교체 자체가 아니라 대화와 작업의 연속이다.
  - task 목록 노출이나 화면 열림은 서버 권한과 실제 요청 성공을 보장하지 않는다.
  - 3회 반복은 종료 타이밍, 인증 재기록, refresh rotation의 일회성 성공을 걸러낸다.
- 기각 대안:
  - UI에 대상 이메일이 보이면 통과: 실제 작업 가능성을 입증하지 못한다.
  - 사용량 변화만 확인: task 접근과 연속성을 입증하지 못한다.
  - 기존 내용을 복사해 B의 새 task 생성: 같은 대화가 아니며 중복·유출 위험이 있다.
  - 1회 왕복: 경쟁 조건과 토큰 갱신 문제를 놓칠 가능성이 높다.
- 재검토 트리거:
  - 없음. 동일 task 연속성이 더 이상 제품 목적이 아닐 때만 새 제품 요구사항으로 다시 합의한다.
- 실패 처리: B 또는 복귀 A에서 같은 task의 실제 메시지가 한 번이라도 구조적으로 불가능하면 Spike FAIL이다. 메뉴바 구현을 중단한다.
- 후속 결정: ADR-027은 사용자 확인상 기능 왕복이 성공한 상태에서 개발 전 증거 형식만 유예한다. 구조적 실패 처리와 MVP 완료·배포 전 정식 증거 요구는 유지한다.

## ADR-004: Spike는 재사용 가능한 Swift CLI core로 만든다

- 상태: 승인
- 결정: 1단계는 Swift CLI로 환경 진단, 프로세스 제어, 인증 교체, 검증, 롤백을 구현한다. 2단계 메뉴바 앱이 동일 core를 사용한다.
- 이유:
  - macOS 프로세스, bundle, LaunchServices, Keychain과 자연스럽게 통합된다.
  - 검증 코드와 제품 코드의 동작 차이를 줄인다.
  - shell Spike를 버리고 다시 구현하는 비용을 피한다.
- 기각 대안:
  - shell-only Spike: 빠르지만 프로세스 분류, 상태 머신, 앱 재사용성이 약하다.
  - UI부터 구현: 핵심 가설 실패 시 UI가 전부 매몰 비용이 된다.
  - 별도 Python helper: 배포 런타임과 macOS 통합 부담이 늘어난다.
- 재검토 트리거:
  - Swift에서 공식 앱 프로세스나 app-server 통신을 검증할 수 없는 구체적 차단점 발견
  - 단, 진단용 shell 명령 보조는 허용하되 전환 로직의 기준 구현은 Swift로 유지한다.

## ADR-005: 신규 소형 앱을 만들고 Mobius는 선택적으로만 참고한다

- 상태: 승인
- 결정: Mobius 전체 포크가 아닌 독립 Swift 프로젝트를 만든다. UI 패턴이나 검증된 작은 구현을 가져올 경우 필요한 코드만 감사하고 MIT 고지를 지킨다.
- 이유:
  - Mobius의 현재 Codex 경로는 실행 중 인증 교체와 직접 usage/OAuth 처리 등 요구사항과 다른 전제를 가진다.
  - Claude, 자동 전환, primary/fallback 등 불필요한 범위가 크다.
  - 핵심 제품은 최대 3개 계정의 안전한 수동 전환뿐이다.
- 기각 대안:
  - Mobius 전체 포크 후 삭제: 제거·검증 범위와 공급망 면적이 커진다.
  - Mobius를 그대로 사용: 공식 Codex 앱 정상 종료와 완전한 트랜잭션 요구를 충족하지 않는다.
- 재검토 트리거:
  - Mobius가 동일한 공식 앱 종료, file lock, 저널, 이메일 검증, 롤백 구조를 공식 제공함
  - 재사용 비용이 신규 core보다 명확히 작다는 코드 감사 결과가 나옴

## ADR-006: MVP는 기본 `~/.codex`만 지원한다

- 상태: 승인
- 결정: 사용자 지정 `CODEX_HOME`은 지원하지 않는다. 환경변수나 설정이 기본 경로와 다르면 전환을 차단한다.
- 이유:
  - 사용자의 현재 환경과 제품 목표가 기본 경로다.
  - 경로별 프로세스 소유권 판정과 다중 홈 동시 실행은 Spike 범위를 불필요하게 넓힌다.
  - 기본 인증 변경이 공식 앱과 새 CLI에 미치는 영향을 명확히 설명할 수 있다.
- 기각 대안:
  - 임의 `CODEX_HOME` 지원: 잘못된 파일을 바꾸거나 실행 중인 다른 홈을 놓칠 위험이 커진다.
  - 계정별 `CODEX_HOME`: ADR-001의 공용 task 목표와 충돌한다.
- 재검토 트리거:
  - MVP 안정화 후 실제 사용자 요구가 생김
  - 공식 앱이 사용자 지정 경로와 프로세스 소유권을 안정적으로 노출함

## ADR-007: 인증 전환은 `auth.json`, 계정 검증은 `account/read` 이메일이다

- 상태: 승인
- 결정:
  - 저장 단위는 정상 로그인에서 얻은 완전한 `auth.json` blob이다.
  - 활성 파일은 기본 `~/.codex/auth.json`이다.
  - 완료 판정은 공개 app-server `account/read`의 이메일 완전 일치다.
  - 모델 prompt나 사용량 변화로 계정을 검증하지 않는다.
- 이유:
  - 파일 기반 인증은 현재 공식 문서와 로컬 동작에서 확인됐다.
  - `account/read`는 모델 요청 없이 현재 계정 이메일과 plan을 제공한다.
  - 현재 공개 응답에는 MVP가 의존할 안정적인 `userId + workspaceAccountId` 조합이 없다.
  - 지원 프로필은 서로 다른 이메일이라 MVP 식별에 충분하다.
- 기각 대안:
  - 토큰 내부 claim 파싱만 사용: 서버가 실제로 수용한 현재 계정을 입증하지 못한다.
  - `userId + workspaceAccountId`: 공개 `account/read` 계약으로 안정적으로 확보되지 않는다.
  - 남은 사용량 비교: 값이 같거나 변화가 늦을 수 있고 계정 신원 검증이 아니다.
  - 테스트 prompt 전송: task 생성과 quota 소비라는 부작용이 있다.
- 재검토 트리거:
  - 같은 이메일의 여러 workspace 지원이 필요함
  - `account/read`에서 이메일이 제거되거나 의미가 바뀜
  - 공식 API가 안정적인 불변 사용자·workspace 식별자를 제공함
- 주의: 이메일은 진단 로그에서 마스킹한다. 등록·검증용 원문은 필요한 최소 범위에서만 취급한다.

## ADR-008: 현재 인증은 전환 직전에 최신화한다

- 상태: 승인
- 결정: 공식 앱 종료가 완료된 뒤 최신 `auth.json`을 현재 등록 프로필의 저장 인증으로 갱신한다. 현재 이메일이 해당 프로필과 일치할 때만 갱신한다.
- 파생 안전 규칙: 비활성 대상 인증은 격리 홈에서 먼저 `refreshToken: false`로 이메일을 확인한 뒤 `refreshToken: true`로 유효성을 검증한다. 두 응답이 대상 이메일과 일치하고 갱신본의 안전 저장까지 성공한 경우에만 대상 저장본을 교체한다. 실패하면 active auth를 변경하지 않고 대상 프로필을 보존한다. 명시적 인증 거부만 `재로그인 필요`, 네트워크·서버 오류는 `검증 불가—재시도`, credential-store write 실패는 저장소 오류로 분류한다.
- 현재 인증 갱신 직전에는 `refreshingCurrent`, 대상 검증·갱신 직전에는 `validatingTarget`을 각각 내구성 있게 기록한다. 대상 refresh 실패가 네트워크·서버 오류라면 폐기된 token으로 단정하지 않고, 안전하게 전환을 중단한다.
- 이유:
  - Codex가 access token이나 refresh token을 회전했을 수 있다.
  - 최초 캡처본만 복원하면 재로그인 또는 refresh 실패가 생길 수 있다.
  - 이메일 일치 조건이 외부 로그인 후 잘못된 프로필 덮어쓰기를 막는다.
- 기각 대안:
  - 최초 캡처를 영구 사용: 오래된 refresh 상태 위험이 있다.
  - 현재 파일을 무조건 활성 프로필에 저장: 미등록 외부 로그인이 기존 프로필을 파괴할 수 있다.
  - 앱 실행 중 먼저 저장: 종료 과정의 마지막 토큰 갱신을 놓칠 수 있다.
- 재검토 트리거:
  - 공식 인증 저장이 회전하지 않는다고 문서로 보장됨
  - Keychain 기반 공식 multi-account API가 제공됨

## ADR-009: 정상 종료 후 exact 앱 소유 잔존은 다시 물은 뒤 SIGTERM한다

- 상태: 승인
- 결정:
  - 공식 앱에는 정상 종료를 요청한다.
  - 1초 뒤에도 남은 프로세스 중 종료 전에 확인한 PID, 시작 시각, 실행 경로가 모두 같은 앱 소유 프로세스가 있으면 별도 확인을 표시한다.
  - 사용자가 `TERMINATE`로 승인한 경우에만 `SIGTERM`을 한 번 보낸다. 거부·EOF·다른 입력이면 인증 무변경으로 차단한다.
  - `SIGTERM` 뒤에도 종료되지 않거나 identity가 달라지면 인증을 바꾸지 않는다.
  - 독립 Codex CLI/app-server는 자동 종료하지 않는다.
  - 독립 프로세스가 남으면 PID와 안전한 작업 경로를 표시하고 전환을 차단한다.
  - 분류 불명 프로세스와 새로 나타난 프로세스는 자동 종료하지 않는다.
  - `SIGKILL`은 Spike와 제품 모두 제공하지 않는다.
- 이유:
  - 실행 중 프로세스가 이전 인증을 다시 기록할 수 있다.
  - 독립 CLI에는 진행 중인 사용자 작업과 미저장 상태가 있을 수 있다.
  - exact identity 제한과 `SIGKILL` 금지가 PID 재사용·작업 손실 위험을 줄인다.
- 기각 대안:
  - 모든 관련 프로세스 `kill`: 독립 작업 손실과 오탐 위험이 크다.
  - 잔존 앱 프로세스를 무기한 차단: 정상 종료 뒤 재부모화된 앱 worker 때문에 전환이 불가능해진다.
  - 앱 프로세스만 확인: 독립 CLI의 인증 갱신 경쟁을 놓친다.
  - 실행 중에도 파일 교체: 가장 위험한 race를 의도적으로 허용한다.
- 재검토 트리거:
  - 공식 API가 안전한 세션 drain 또는 account switch를 제공함
  - 독립 CLI가 인증 파일을 절대 쓰지 않는다고 보장됨

## ADR-010: 실행 중 앱에서는 매번 종료 확인을 받는다

- 상태: 승인
- 결정: 대상 카드 선택 시 공식 앱이 실행 중이면 매번 정상 종료와 전환 확인을 표시한다. active task 자동 감지는 MVP에 넣지 않는다.
- 이유:
  - task 실행 상태를 안정적으로 판정하는 공식 계약이 확인되지 않았다.
  - 확인은 사용자가 진행 중 작업을 판단할 마지막 안전장치다.
- 기각 대안:
  - 즉시 자동 종료: 사용자가 진행 중 작업을 놓칠 수 있다.
  - active-turn 감지 후 조건부 확인: MVP 범위와 불확실성이 증가한다.
- 재검토 트리거:
  - 공식 app-server가 실행 중 turn과 안전 종료 상태를 안정적으로 제공함
  - 반복 사용 데이터상 확인 피로가 큰 문제로 확인됨

## ADR-011: 전환은 원자적 상태 머신과 프로세스 간 lock을 사용한다

- 상태: 승인
- 결정: 전환 전체를 하나의 트랜잭션으로 구현한다. `flock` 기반 배타 lock, 단계별 저널, 동일 파일시스템 임시 파일, `0600`, rename을 사용한다.
- 기준 단계:
  1. 환경 사전 검사
  2. 배타 lock 획득
  3. 비밀 없는 저널 시작
  4. 현재 신원 확인
  5. 공식 앱 정상 종료와 프로세스 정리 확인
  6. `refreshingCurrent` 지속 후 최신 현재 인증 갱신·보존
  7. `validatingTarget` 지속 후 대상 인증의 이메일 사전 확인·refresh·안전 저장
  8. 대상 인증 원자 교체
  9. 공식 앱 실행
  10. 대상 이메일 확인
  11. 활성 프로필 커밋
  12. 저널 삭제와 lock 해제
- 이유:
  - 활성 파일, 프로필 저장소, 레지스트리가 서로 다른 시점에 갱신된다.
  - 프로세스 내부 lock만으로 CLI와 메뉴바 앱의 동시 전환을 막을 수 없다.
  - 직접 overwrite는 crash 시 부분 JSON을 노출할 수 있다.
- 기각 대안:
  - `NSLock`만 사용: 다른 프로세스를 막지 못한다.
  - `auth.json` 직접 쓰기: 부분 쓰기와 손상 위험이 있다.
  - 인증 교체 직후 active ID 갱신: 실제 앱 계정 검증 전 거짓 성공 상태가 된다.
- 재검토 트리거:
  - 공식 원자 계정 전환 API가 제공됨

## ADR-012: 프로덕션 비활성 인증은 macOS Keychain에 저장한다

- 상태: 승인
- 결정:
  - Spike는 한정된 로컬 `0600` 파일 저장을 허용한다.
  - 메뉴바 제품은 각 프로필의 인증 blob을 Keychain에 저장한다.
  - 파일시스템에는 활성 `~/.codex/auth.json`만 materialize한다.
- 이유:
  - `auth.json`에는 access, refresh, identity token이 포함될 수 있다.
  - Application Support의 평문 스냅샷은 편리하지만 제품 보안 기준에 부족하다.
  - Keychain은 macOS 개인 앱의 표준 비밀 저장소다.
- 기각 대안:
  - Application Support에 영구 `0600` 파일: 권한은 노출면을 줄이지만 평문 비밀이다.
  - 자체 암호화 파일: 키 저장 문제가 다시 생기고 복잡성만 늘어난다.
  - 인증 필드별 분해 저장: 공식 파일 형식 변화에 더 취약하다.
- 재검토 트리거:
  - 공식 앱이 다계정 Keychain 항목 관리 API를 제공함
  - 팀 배포에서 별도 보안 요구가 생김

## ADR-013: 실패 시 새 앱을 닫고 이전 계정까지 검증 복원한다

- 상태: 승인
- 결정: 대상 검증 또는 실행이 실패하면 새로 실행한 앱/app-server를 정상 종료하고 이전 인증을 원자 복원한다. 이후 순서는 **이전 이메일 검증 → registry previous durable commit → journal unlink와 parent directory `fsync` → 이전 계정 앱 재실행**으로 고정한다.
- 이유:
  - 파일만 되돌리고 앱을 둔 채로 두면 메모리와 디스크 계정이 불일치할 수 있다.
  - 복원 이메일 확인 없이 재실행 성공을 선언할 수 없다.
- 롤백 실패 결정:
  - 공식 앱을 재실행하지 않는다.
  - configured credential store의 검증된 previous/target 원본을 유지한다.
  - 저널과 비밀 없는 진단을 보존한다.
  - 수동 복구 안내를 표시한다.
- 기각 대안:
  - 실패한 대상 앱을 그대로 둠: 잘못된 인증 재기록 위험이 있다.
  - 프로필 삭제 후 로그인 유도: 복구 가능한 인증을 파괴한다.
  - 검증 없이 이전 파일만 복사: 손상 또는 잘못된 복원을 놓친다.
- 재검토 트리거:
  - 공식 앱이 실행 중 안전한 인증 reload와 rollback API를 제공함

## ADR-014: crash 복구용 저널에는 비밀을 넣지 않는다

- 상태: 승인
- 결정: 영속 저널 필드는 `schemaVersion`, `transactionId`, `phase`, `previousProfileId`, `targetProfileId`, `startedAt`, `updatedAt`으로 제한한다. 시작 시 미완료 저널을 해석해 보수적으로 이전 인증을 복원한다.
- 내구성 규칙:
  - 저널과 registry는 같은 디렉터리의 `0600` 임시 파일에 완전히 쓰고 file `fsync` → atomic rename → parent directory `fsync` 순서로 지속한다.
  - 각 phase는 그 phase가 보호하는 다음 side effect보다 먼저 지속돼야 한다.
  - 성공은 registry 커밋을 먼저 지속한 뒤 journal unlink와 parent directory `fsync`로 끝낸다.
  - active auth 변경 전 취소·차단도 journal unlink와 parent directory `fsync`로 끝낸다.
  - 잘리거나 schema가 잘못된 저널은 자동 복구를 추정하지 않고 STOP한다.
- 이유:
  - 앱 crash, 전원 종료, 재부팅은 프로세스 메모리 상태를 잃게 한다.
  - 인증 사본을 저널에 넣으면 별도 비밀 저장소가 하나 더 생긴다.
- 기각 대안:
  - 저널 없음: active 파일과 registry 불일치를 자동 판정하기 어렵다.
  - 전체 auth 백업을 저널에 저장: 비밀 노출면이 커진다.
  - 단계마다 양쪽 저장소를 동기 쓰기: crash 원자성을 보장하지 않는다.
- 재검토 트리거:
  - 전환 전체를 보장하는 단일 공식 트랜잭션 API가 제공됨

## ADR-015: MVP는 2개 계정이지만 내부 모델은 배열이다

- 상태: ADR-028로 대체
- 결정: 사용자 흐름은 개인·회사 정확히 2개 프로필만 허용한다. 데이터 모델과 core API는 프로필 배열과 profile ID를 사용한다.
- 이유:
  - 현재 요구는 2개라 UI, 등록, 복구 경우의 수를 제한할 수 있다.
  - `personalAuth`, `workAuth`처럼 필드를 하드코딩하면 3개 확장 시 migration과 로직 재작성이 필요하다.
  - 배열은 과도한 추상화 없이 자연스러운 데이터 표현이다.
- 기각 대안:
  - 처음부터 무제한 계정 UI: Spike 전에 관리 복잡도를 늘린다.
  - 개인·회사 전용 필드 두 개: 3개 확장 비용이 커진다.
- 재검토 트리거:
  - MVP 안정화 후 세 번째 계정 요구
  - 2개 제한이 실제 사용자 흐름을 막는다는 증거

## ADR-016: 초기 등록은 공식 `codex login`, 나중에 격리 app-server 로그인이다

- 상태: 승인
- 결정:
  - Spike와 MVP 초기 버전은 사용자가 공식 `codex login`으로 정상 로그인한 인증을 helper가 캡처한다.
  - 추가 프로필 등록이 끝나면 helper가 등록 시작 전 활성 프로필을 자동 복원한다.
  - 전환 가설이 입증된 뒤 격리된 임시 `CODEX_HOME`의 app-server 로그인 흐름을 추가할 수 있다.
- 이유:
  - 공식 로그인 경로를 그대로 사용해 OAuth 세부 구현을 피한다.
  - 로그인 UI보다 계정 전환 안전성 검증이 먼저다.
  - 추가 등록 후 자동 복귀가 사용자의 원래 작업 상태를 보존한다.
- 기각 대안:
  - 처음부터 직접 OAuth/device-code 구현: client ID, scope, refresh 계약 유지보수 위험이 있다.
  - 계정 추가 후 새 계정을 활성 상태로 둠: 사용자가 원래 계정으로 돌아가는 추가 절차가 필요하다.
- 재검토 트리거:
  - Spike 통과와 메뉴바 전환 안정화
  - 공식 app-server 로그인 API의 지속 가능성 확인

## ADR-017: 미등록 외부 로그인은 자동 덮어쓰기하지 않는다

- 상태: 승인
- 결정: 현재 `account/read` 이메일이 어느 등록 프로필과도 일치하지 않으면 전환을 차단한다. 사용자가 새 등록 또는 외부 인증 폐기를 명시적으로 선택해야 한다.
- 이유:
  - helper 밖 `codex login`이 기존 활성 프로필을 잘못 갱신할 수 있다.
  - 이메일만으로 자동 병합하면 어떤 저장 인증이 권위 있는지 알 수 없다.
- 기각 대안:
  - active profile에 자동 저장: 알려진 인증을 잃을 수 있다.
  - 미등록 인증 자동 삭제: 사용자의 방금 로그인한 계정을 파괴한다.
- 재검토 트리거:
  - 공식 다계정 레지스트리와 불변 profile ID가 제공됨

## ADR-018: 만료·취소된 대상 프로필은 보존한다

- 상태: 승인
- 결정: 대상 인증이 만료 또는 취소돼 검증 실패하면 이전 계정으로 롤백하고 대상 프로필에 `재로그인 필요`를 표시한다. 자동 삭제하지 않는다.
- 이유:
  - 일시적 네트워크 실패와 영구 인증 취소를 즉시 구분하기 어렵다.
  - 라벨, 등록 관계, 복구 가능 인증을 보존하는 편이 안전하다.
- 기각 대안:
  - 실패 즉시 프로필 삭제: 복구와 진단 기회를 잃는다.
  - 로그인 화면 상태로 대상 앱 유지: 이전 계정 작업 복원을 방해한다.
- 재검토 트리거:
  - 공식 API가 취소 상태를 확정적으로 구분하고 안전한 재인증을 지원함

## ADR-019: 이미 활성인 계정 선택은 무변경 동작이다

- 상태: 승인
- 결정: 대상이 현재 활성 프로필이면 인증 파일을 쓰거나 앱을 재시작하지 않는다. 실행 중이면 Codex 창을 활성화하고, 닫혀 있으면 검증 후 실행한다.
- 이유:
  - 불필요한 파일 쓰기와 토큰 race를 없앤다.
  - 사용자의 카드 클릭 기대를 충족한다.
- 기각 대안:
  - 매번 전체 전환 실행: 위험과 대기만 늘어난다.
  - 아무 반응 없음: UI가 고장 난 것처럼 보인다.
- 재검토 트리거:
  - 없음. 공식 앱의 활성화 동작이 바뀌면 창 활성화 구현만 조정한다.

## ADR-020: 앱이 닫혀 있으면 전환 후 실행한다

- 상태: 승인
- 결정: 공식 앱이 닫힌 상태에서 대상 카드를 선택하면 종료 확인 없이 안전한 전환을 수행하고 공식 앱을 연다.
- 이유:
  - 종료할 작업이 없으므로 확인이 불필요하다.
  - 사용자가 계정 선택과 앱 실행을 한 번에 기대한다.
- 기각 대안:
  - 파일만 바꾸고 앱을 열지 않음: 클릭 결과를 확인하기 어렵다.
  - 항상 확인: 불필요한 마찰이다.
- 재검토 트리거:
  - 백그라운드 독립 프로세스가 자주 남아 사용자 오해가 발생함. 이 경우 차단 설명을 개선하며 자동 종료는 하지 않는다.

## ADR-021: 사용량은 후속 읽기 전용 기능이다

- 상태: 승인
- 결정: 메뉴바 MVP는 계정, 활성 이메일, 수동 전환만 제공한다. 5시간·주간 잔여량과 초기화 시각은 전환 안정화 후 추가한다.
- 이유:
  - 사용량은 사용자가 원하지만 인증 전환의 성립 조건은 아니다.
  - 비활성 계정 조회, stale 정책, 토큰 갱신이 핵심 Spike를 흐린다.
  - 공개 app-server의 `account/rateLimits/read`를 후속 경계면으로 사용할 수 있다.
- 기각 대안:
  - MVP에 사용량 포함: 일정과 실패 원인이 결합된다.
  - 사용량을 계정 검증에 사용: 지연·동률·캐시 때문에 신뢰성이 낮다.
  - 비공식 usage endpoint 직접 호출: 서버 내부 계약과 OAuth 값을 앱이 떠안는다.
- 재검토 트리거:
  - Spike와 MVP 전환이 안정화됨
  - 비활성 프로필 조회를 격리 app-server로 안전하게 구현 가능함
- 후속 원칙: 사용량 실패는 전환이나 프로필 상태를 바꾸지 않는다.

## ADR-022: 전환은 데스크톱 전용이 아니라 기본 Codex 인증 전체에 적용된다

- 상태: 승인
- 결정: `~/.codex/auth.json` 교체는 공식 앱과 전환 후 시작되는 새 CLI 세션 모두에 영향을 준다고 제품에서 명시한다.
- 이유:
  - 동일 기본 인증 파일을 공유하므로 데스크톱만 분리해 바꿀 수 없다.
  - 이 사실을 숨기면 사용자가 CLI 요청을 잘못된 계정으로 보낼 수 있다.
- 기각 대안:
  - 데스크톱 전용이라고 표현: 실제 동작과 다르다.
  - CLI용 별도 `CODEX_HOME` 자동 설정: 사용자의 셸과 기존 작업을 침범한다.
- 재검토 트리거:
  - 공식 앱이 데스크톱 전용 인증 저장소를 제공함

## ADR-023: Codex 업데이트는 보호된 시도 또는 사전 차단으로 처리한다

- 상태: 승인
- 결정:
  - bundle identifier, 기본 인증 경로, JSON 유효성, app-server `account/read` 계약이 깨지면 전환 전에 차단한다.
  - 버전·build만 달라지고 계약 검사가 통과하면 경고 후 보호된 전환을 시도할 수 있다.
  - 실패하면 자동 롤백한다.
- 이유:
  - 공식 앱의 내부 실행 파일명과 process tree는 바뀔 수 있다.
  - 버전 변경만으로 영구 차단하면 제품이 지나치게 취약하다.
  - 핵심 계약 검사는 실제 안전 조건을 직접 확인한다.
- 기각 대안:
  - 모든 업데이트 무조건 허용: 호환성 파손을 인증 변경 후 발견한다.
  - 버전 allowlist만 허용: 사소한 업데이트마다 제품이 멈춘다.
- 재검토 트리거:
  - 공식 버전 호환성 API 또는 안정적인 account switching API가 제공됨

## ADR-024: 최소 로컬 진단만 남긴다

- 상태: 승인
- 결정: 시각, Codex 버전·build, 전환 단계, 마스킹 이메일, 오류, 필요 시 PID와 안전한 작업 경로만 로컬에 기록한다. 토큰, 전체 인증, 쿠키, authorization header, 원시 command line은 금지한다.
- 이유:
  - 전환 race와 업데이트 문제를 재현하려면 단계 정보가 필요하다.
  - 인증 비밀이나 command line은 진단 가치보다 유출 위험이 크다.
- 기각 대안:
  - 로그 없음: 실패 원인과 롤백 상태를 복원하기 어렵다.
  - verbose 원문 로그: 보안 사고 위험이 크다.
  - 실제 이메일 영구 기록: 필요 이상의 개인정보다.
- 재검토 트리거:
  - 배포 범위가 팀 단위로 커져 지원 번들이 필요함. 이 경우에도 사용자의 명시적 생성과 추가 redaction을 요구한다.

## ADR-025: 개인·GitHub 배포 후 서명·공증한다

- 상태: 승인
- 결정: 초기 제품은 개인 사용과 GitHub 저장소 배포를 목표로 한다. App Store sandbox를 목표로 하지 않는다. 안정화 후 Developer ID 서명과 공증을 추가한다.
- 이유:
  - 기본 `~/.codex` 파일, 실행 프로세스 검사, 앱 정상 종료, Keychain 사용이 핵심 기능이다.
  - App Store sandbox 제약은 초기 검증을 방해한다.
  - 서명·공증은 Spike 성립 여부와 독립적이다.
- 기각 대안:
  - 처음부터 App Store: 권한·샌드박스 설계가 제품 핵심보다 커진다.
  - 영구 미서명 배포: 사용자 신뢰와 Gatekeeper 경험이 나쁘다.
- 재검토 트리거:
  - MVP 안정화와 공개 배포 준비
  - 조직 배포 또는 자동 업데이트 요구

## ADR-026: 실제 회사 데이터 없이 검증한다

- 상태: 승인
- 결정: 동일 task Spike는 가짜 데이터와 무해한 prompt만 사용한다. 교차 계정 task 접근이 확인되더라도 회사 데이터 정책 준수를 제품이 대신 보장하지 않는다.
- 이유:
  - 공유 task 자체가 계정 간 정보 노출 가능성을 가진다.
  - 제품은 편의 도구이며 데이터 분류·DLP 도구가 아니다.
- 기각 대안:
  - 실제 업무 task로 검증: 불필요한 정책·기밀 위험이 있다.
- 재검토 트리거:
  - 회사 보안팀의 명시적 승인과 별도 테스트 계획이 있음

## ADR-027: B-010 증거 공백을 수용하고 메뉴바 개발을 시작한다

- 상태: 승인 (2026-07-30)
- 결정:
  - 사용자 확인상 같은 task에서 A↔B 기능 왕복 3회와 실제 메시지 응답이 완료됐고 구조적 ownership 실패는 관찰하지 않았다.
  - cycle nonce와 단계별 task ID 기록이 없으므로 B-010을 정식 PASS로 표시하지 않는다.
  - 사용자가 이 증거 형식 공백을 수용하고 `MenuBarExtra` MVP 구현 시작을 승인했다.
  - B-010 정식 증거는 MVP 완료·배포 전 인수 게이트로 유지한다.
- 이유:
  - 제품 가설과 자동 롤백은 실환경에서 기능적으로 확인됐다.
  - 남은 공백은 동작 결함이 아니라 실행 기록 형식이다.
  - 메뉴바 구현은 검증된 Core를 재사용하며 실제 auth 전환 없이 테스트할 수 있다.
- 기각 대안:
  - B-010을 정식 PASS로 기록: 보존하지 않은 증거를 사후 추정하므로 금지한다.
  - B-010을 완전히 삭제: 구조적 same-task 실패를 릴리스 전에 잡을 수 없다.
- 재검토 트리거:
  - 메뉴바 앱으로 B-010 정식 증거를 확보함
  - same-task ID 변경, copy/fork 또는 account ownership 오류가 관찰됨

## ADR-028: MVP는 최대 3개 계정을 지원한다

- 상태: 승인 (2026-07-30)
- 결정:
  - 메뉴바 UI, registry, 등록 정책은 서로 다른 이메일의 프로필을 최대 3개 허용한다.
  - 네 번째 등록은 기존 auth, credential store, registry를 바꾸지 않고 거부한다.
  - 추가 등록 후에는 등록 시작 전 활성 프로필을 검증 복원한다.
  - 기존 배열·profile UUID·registry schema를 유지하므로 migration은 없다.
- 이유:
  - 메뉴바 UI 구현 전 실제 3계정 요구가 확인됐다.
  - Core가 배열과 profile ID를 사용해 상한과 capture 복구 가정만 일반화하면 된다.
  - 3개 상한은 현재 요구를 충족하면서 등록·복구 경우의 수를 제한한다.
- 기각 대안:
  - 2개 유지: 실제 사용자 흐름을 막는다.
  - 무제한 계정: 현재 필요 없는 UI·검증 복잡도를 추가한다.
- 대체 범위: ADR-002와 ADR-015의 계정 수 제한만 대체한다. A↔B B-010 실증 기준은 유지한다.
- 재검토 트리거:
  - 네 번째 계정 요구가 확인됨

## 2. 결정 간 핵심 제약

아래 제약은 하나라도 깨지면 구현을 계속하지 않는다.

1. 같은 task의 A↔B 실제 메시지 왕복 기능은 유지해야 한다. ADR-027은 개발 전 증거 형식만 유예하며 B-010 정식 증거는 MVP 완료·배포 전에 필요하다.
2. 전환 완료는 `account/read` 이메일 일치 후에만 커밋한다.
3. 현재 인증 최신화는 현재 이메일이 등록 프로필과 일치할 때만 한다.
4. 공식 앱은 정상 종료만 사용한다.
5. 독립 Codex 프로세스가 남으면 인증을 변경하지 않는다.
6. 비활성 인증은 제품에서 Keychain에 둔다.
7. 대상 실패 시 이전 계정 검증 복원, 복원 실패 시 앱 미실행 원칙을 지킨다.
8. `auth.json` 외 공용 상태와 공식 앱 번들을 수정하지 않는다.
9. MVP는 최대 3개 프로필만 허용하고 네 번째 등록은 무변경 거부한다.
10. MVP는 사용량, 자동 전환, 계정별 환경을 포함하지 않는다.
11. 실제 인증값과 이메일을 문서·로그·fixture에 넣지 않는다.

## 3. 재검토 절차

결정을 바꿀 때는 다음을 기록한다.

1. 어떤 재검토 트리거가 발생했는가
2. 공식 문서 또는 재현 가능한 실험 근거는 무엇인가
3. 동일 task 연속성, 인증 무결성, 사용자 작업 손실 위험이 어떻게 변하는가
4. 기존 Keychain 항목, 저널, registry migration이 필요한가
5. 실패 시 이전 버전으로 되돌리는 방법은 무엇인가

편의만 좋아지고 위 핵심 제약이 약해지는 변경은 승인하지 않는다.

## 4. 구현 task 시작용 요약

Swift CLI Core와 실환경 전환·롤백 검증은 완료됐다. 다음 구현은 Core를 재사용하는 `CodexAccountMenuBar`다. 기본 `~/.codex`만 지원하고 비활성 인증은 Keychain에 둔다. 공식 앱 정상 종료, 독립 CLI 차단, `flock`, 비밀 없는 저널, `account/read` 이메일 검증, 전체 롤백 불변조건은 유지한다. 최대 3개 프로필을 노출하고 사용량은 후속이다. ADR-027에 따라 개발은 시작하되 B-010 정식 증거는 MVP 완료·배포 전 확보한다.
