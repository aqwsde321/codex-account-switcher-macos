# Codex Account Switcher 제품 요구사항

- 상태: 메뉴바 MVP 개발 승인
- 기준일: 2026-07-30
- 대상: macOS 공식 Codex 앱용 최대 3개 계정 전환 helper
- 문서 역할: Spike와 MVP를 새 task에서 재개할 때 사용하는 제품 기준 문서

## 1. 문서 우선순위

이 문서는 사용자와의 최종 grilling 합의를 반영한다. 초기 첨부 문서와 충돌하면 이 문서가 우선한다.

특히 다음 초기안은 폐기됐다.

- Mobius 전체 포크: 폐기. 신규 소형 Swift 앱을 만든다.
- `userId + workspaceAccountId` 식별: MVP에서는 사용하지 않는다. `account/read`의 이메일을 사용한다.
- 사용량 게이지를 MVP에 포함: 후속 기능으로 연기한다.
- 실패 시 계정별 환경으로 자동 전환: 폐기. 올바른 인증 전환 뒤에도 동일 task 재개가 ownership 구조 때문에 불가능하면 제품 구현을 중단한다.
- Spike용 shell 중심 구현: 폐기. 제품에서 재사용할 Swift CLI core로 만든다.

## 2. 제품 요약

최대 3개 ChatGPT 로그인의 Codex 인증을 빠르게 바꾸는 macOS 메뉴바 앱을 만든다. 계정 카드를 선택하면 helper가 공식 Codex 앱을 정상 종료하고, 공용 `~/.codex/auth.json`만 대상 계정 인증으로 원자 교체한 뒤 앱을 다시 실행한다. `account/read`가 반환한 이메일로 실제 활성 계정을 확인한다.

이 제품은 계정별 격리 도구가 아니다. `config.toml`, skills, sessions, history, SQLite, MCP 설정 등 로컬 Codex 상태를 공유한 채 인증만 전환하는 편의 도구다.

## 3. 문제와 목적

### 3.1 문제

공식 Codex 앱은 로컬 다계정 전환 UI를 제공하지 않는다. 사용자는 개인·회사 계정을 오갈 때 로그인 절차를 반복해야 한다. 단순 파일 교체는 앱 메모리, app-server, 독립 CLI, 토큰 갱신 때문에 이전 인증이 다시 기록될 위험이 있다.

### 3.2 제품 목적

1. 최대 3개 계정 간 수동 전환을 한 번의 메뉴바 동작으로 만든다.
2. 전환 중 인증 손상, 오래된 토큰 복원, 잘못된 계정 실행을 막는다.
3. 하나의 로컬 task를 두 계정에서 그대로 열고 실제 작업을 이어갈 수 있는지 먼저 검증한다.
4. Spike에서 검증된 동일 core를 메뉴바 앱에서 재사용한다.

### 3.3 가장 중요한 성공 가설

공식 앱과 관련 프로세스가 완전히 종료된 뒤 `~/.codex/auth.json`만 교체하면, 공용 로컬 task 및 설정은 유지되고 실제 요청 계정만 바뀐다.

이 가설은 화면 표시가 아니라 같은 task에서 양쪽 계정의 실제 메시지 성공으로 판정한다.

## 4. 사용자와 페르소나

### 4.1 주 사용자

- 한 Mac에서 최대 3개의 별도 ChatGPT 로그인을 사용하는 개발자
- 여러 계정에서 동일한 Codex 설정과 로컬 task를 이어 쓰려는 사용자
- 매 전환 시 앱 종료와 재로그인을 수동으로 반복하고 싶지 않은 사용자

### 4.2 사용자 전제

- 계정 간 로컬 상태 공유를 의도적으로 선택한다.
- 회사 데이터가 개인 계정으로 전송될 수 있는 교차 계정 작업의 정책 책임을 이해한다.
- 회사 보안 정책이 계정 간 task 공유를 금지하면 이 제품을 사용하지 않는다.

## 5. 용어

- **프로필**: 계정 라벨, 검증 이메일, configured credential-store 항목 식별자, 마지막 사용 시각을 가진 로컬 레코드
- **활성 프로필**: 현재 `~/.codex/auth.json`과 일치한다고 검증된 등록 프로필
- **공용 상태**: `auth.json`을 제외한 기본 `~/.codex` 및 공식 앱의 로컬 상태
- **전환**: 현재 인증 보존, 대상 인증 적용, 앱 재실행, 대상 이메일 검증을 하나로 묶은 트랜잭션
- **공식 앱 프로세스**: bundle identifier가 `com.openai.codex`인 앱과 그 앱이 시작한 helper/app-server
- **독립 Codex 프로세스**: 공식 앱 자식이 아니며 공용 Codex 인증을 사용할 수 있는 CLI 또는 app-server
- **동일 task 재개**: 계정 A에서 만든 정확히 같은 task를 계정 B에서 열고 새 메시지를 성공시킨 뒤 A에서도 다시 메시지를 성공시키는 것
- **원자 교체**: 동일 파일시스템의 임시 파일을 검증한 후 rename으로 `auth.json`을 한 번에 바꾸는 것
- **저널**: 토큰 없이 schema·transaction·단계·이전/대상 프로필 ID·시각만 고정 7필드로 기록하는 복구 메타데이터

## 8. 사용자 경험

### 8.1 최초 등록

1. 사용자가 공식 `codex login`으로 첫 계정에 로그인한다.
2. 사용자가 프로필 라벨을 정하고 공식 앱 종료·등록·재실행을 확인한다.
3. helper가 공식 앱에 정상 종료를 요청하고 ADR-009의 잔존 프로세스 경계를 적용한다. 독립 CLI·IDE는 자동 종료하지 않는다.
4. process gate가 깨끗할 때만 `account/read`로 이메일을 확인한다.
5. Spike는 `0600` 파일, MVP는 Keychain에 인증을 저장한다.
6. 공식 앱을 등록 계정으로 다시 연다.
7. 로컬 메뉴바 UI에는 계정 구분을 위해 이메일을 표시한다. 진단 로그와 공유용 screenshot에서는 마스킹한다.

### 8.2 추가 계정 등록

1. helper가 등록 시작 전 활성 프로필의 저장 인증이 존재하는지 확인한다.
2. 사용자가 공식 `codex login`으로 다른 계정에 로그인한다.
3. 사용자가 공식 앱 종료·등록·새 계정 활성 유지를 확인한다.
4. helper가 공식 앱에 정상 종료를 요청하고 ADR-009의 잔존 프로세스 경계를 적용한다. 독립 CLI·IDE는 자동 종료하지 않는다.
5. process gate가 깨끗할 때만 `account/read` 이메일로 새 계정임을 확인하고 새 인증을 저장한다.
6. 등록 완료 후 helper가 새 계정을 활성 프로필로 확정하고 해당 계정으로 공식 앱을 다시 연다.
7. 성공 경로에서는 이전 계정을 갱신·복원하지 않는다. 커밋 전 취소나 실패만 저장된 이전 계정으로 롤백하거나 명확히 STOP한다.

MVP는 등록 프로필을 최대 3개로 제한한다. 네 번째 등록은 기존 인증·registry를 바꾸지 않고 거부한다.

### 8.3 계정 전환

앱 실행 중 대상 카드를 선택하면:

1. 종료 및 전환 확인을 표시한다.
2. 전환 lock을 획득하고 저널을 시작한다.
3. 현재 환경과 활성 이메일을 검증한다.
4. 공식 앱에 정상 종료를 요청한다.
5. 1초 뒤에도 종료 전 확인된 앱 소유 프로세스가 남으면 별도 확인을 표시하고, 사용자가 승인한 경우에만 `SIGTERM`을 한 번 보낸다.
6. 종료되지 않은 앱 소유 프로세스나 독립·분류 불명 Codex 프로세스가 남으면 인증 변경 없이 중단한다.
7. `refreshingCurrent`를 내구성 있게 기록한 뒤 기본 홈의 Helper 소유 App Server로 현재 인증을 갱신한다.
8. 현재 이메일이 일치할 때만 갱신된 `auth.json`을 현재 프로필에 저장하고 `currentSaved`를 기록한다.
9. `validatingTarget`을 기록한 뒤 대상 인증을 격리 홈에서 먼저 이메일 확인하고, 이어서 token refresh와 같은 이메일을 확인한다.
10. 갱신된 대상 blob을 configured credential store에 안전하게 저장한 뒤 `targetValidated`를 기록한다.
11. 대상 인증을 `0600`으로 원자 교체한다.
12. 공식 앱을 실행한다.
13. active auth를 격리 verifier에서 읽어 `account/read` 이메일이 대상 프로필과 같은지 확인한다.
14. 성공한 경우에만 활성 프로필을 내구성 있게 갱신하고 저널을 삭제한다.

앱이 이미 종료된 상태라면 종료 확인 없이 2단계부터 진행하고, 성공 후 공식 앱을 실행한다.

### 8.4 이미 활성인 계정 선택

- `auth.json`을 다시 쓰지 않는다.
- 앱이나 app-server를 재시작하지 않는다.
- 실행 중인 공식 Codex 창만 활성화한다.
- 앱이 닫혀 있으면 검증 후 앱을 연다.

### 8.4.1 비활성 프로필 삭제

- 활성 프로필에는 삭제 동작을 제공하지 않는다.
- 비활성 프로필 삭제 전 로컬 profile과 Keychain item만 제거하며 OpenAI 계정·현재 Codex 로그인은 바뀌지 않음을 확인한다.
- 취소를 기본 동작으로 두고, 승인 시 삭제 marker→Keychain item→registry profile→marker 순서로 처리한다.
- 중단된 삭제는 시작 자동 복구가 재개하며 switch journal과 충돌하면 둘 다 보존하고 STOP한다.
- 삭제한 계정은 같은 라벨·이메일로 다시 등록할 수 있으며 새 profile ID를 사용한다.

### 8.5 전환 실패와 롤백

대상 이메일 불일치, 앱 실행 실패, 인증 오류가 발생하면:

1. 새로 실행한 공식 앱과 검증용 app-server를 정상 종료한다.
2. 이전 인증을 원자 복원한다.
3. `account/read`로 이전 이메일을 검증한다.
4. 이전 프로필 registry를 내구성 있게 커밋한다.
5. journal을 unlink하고 parent directory를 `fsync`한다.
6. 위 내구성 정리가 끝난 후에만 이전 계정으로 공식 앱을 다시 실행한다.
7. 대상 프로필은 삭제하지 않고 오류 종류에 맞는 상태로 유지한다.

롤백 자체가 실패하면 공식 앱을 재실행하지 않는다. configured credential store의 검증된 저장본과 미완료 저널을 보존하고, 사용자에게 수동 복구 절차와 비밀 없는 진단 정보를 보여준다.

### 8.6 외부 로그인 감지

helper 밖에서 `codex login`을 실행해 현재 이메일이 등록 프로필과 달라지면 자동 병합하거나 덮어쓰지 않는다. 사용자는 다음 중 하나를 명시적으로 선택해야 한다.

- 현재 인증을 새 프로필로 등록
- 현재 외부 인증을 폐기하고 등록 프로필 복원

MVP가 이미 3개 프로필을 보유하면 새 등록은 제한 안내 후 중단한다.

### 8.7 Codex 업데이트 이후

- bundle identifier, 기본 인증 경로, `auth.json` 유효성, app-server `account/read` 계약을 사전 검사한다.
- 핵심 계약이 깨지면 전환 전에 즉시 차단한다.
- 버전만 바뀌고 계약 검사가 통과하면 경고와 함께 보호된 전환을 한 번 시도할 수 있다.
- 시도 실패 시 자동 롤백한다.

## 9. 기능 요구사항

### FR-01 환경 제한

- MVP는 기본 `~/.codex`만 지원해야 한다.
- `CODEX_HOME`이 다른 경로를 가리키면 전환하지 말고 지원하지 않는 환경으로 표시해야 한다.
- 공식 앱은 bundle identifier를 기준으로 찾고 실제 경로, 실행 파일, 버전, build를 기록해야 한다.

### FR-02 계정 모델

- 프로필 저장 구조는 배열이어야 한다.
- MVP UI와 등록 정책은 프로필을 최대 3개만 허용해야 한다.
- 라벨은 개인·회사를 기본값으로 제공하고 사용자 지정을 허용하되 인증 식별자로 사용하지 않아야 한다.

### FR-03 계정 식별과 검증

- 전환 완료 여부는 app-server `account/read`의 이메일 완전 일치로 판정해야 한다.
- plan, 라벨, 사용량은 식별값으로 사용하지 않아야 한다.
- 계정 검증을 위해 모델 prompt를 전송하면 안 된다.
- 이메일 검증 호출은 task를 만들거나 모델 quota를 소비하는 사용자 요청으로 취급하지 않는다.

### FR-04 인증 저장

- Spike 스냅샷은 `0600`, 상위 디렉터리는 `0700`이어야 한다.
- MVP의 저장 프로필 인증은 macOS Keychain에 있어야 한다.
- 평상시 파일시스템에는 활성 프로필의 `~/.codex/auth.json`만 존재해야 한다.
- 현재 활성 이메일이 등록 프로필과 일치할 때만 전환 직전 최신 `auth.json`으로 해당 Keychain 항목을 갱신해야 한다.
- 대상 저장 인증은 격리 App Server에서 먼저 `refreshToken: false`로 이메일을 확인한 뒤 `refreshToken: true` 검증이 성공한 경우에만 해당 대상 Keychain 항목을 갱신해야 한다.
- 대상 refresh, 이메일 검증, 안전 저장 중 하나라도 실패하면 active auth를 바꾸지 않고 기존 대상 프로필을 보존해야 한다. 명시적 인증 거부일 때만 `재로그인 필요`, 네트워크·서버 오류일 때는 `검증 불가—재시도`로 표시해야 한다.

### FR-05 프로세스 제어

- 공식 앱에는 먼저 정상 종료를 요청해야 한다.
- 1초 뒤에도 남은 프로세스 중 종료 전에 확인한 exact 앱 소유 PID에는 별도 사용자 승인 뒤 `SIGTERM`을 한 번 보낼 수 있다.
- 사용자가 거부하거나 입력을 완료하지 않으면 인증을 바꾸지 않고 차단해야 한다.
- PID 시작 시각이나 실행 경로가 바뀌었거나 `SIGTERM` 뒤에도 제한 시간 안에 끝나지 않으면 인증을 바꾸지 않아야 한다.
- `SIGKILL` 기능을 제공하면 안 된다.
- 공식 앱 자식 프로세스와 독립 Codex 프로세스를 구분해야 한다.
- 독립 프로세스를 자동 종료하면 안 된다.
- 독립 프로세스가 남으면 PID와 작업 경로를 보여주고 전환을 차단해야 한다.

### FR-06 전환 동시성

- 한 번에 하나의 전환만 허용해야 한다.
- 프로세스 내부 lock 외에 `flock` 기반 프로세스 간 lock을 사용해야 한다.
- 메뉴바 앱과 CLI core가 동시에 전환할 수 없어야 한다.

### FR-07 전환 저널

- 인증을 변경하기 전에 저널을 기록해야 한다.
- 저널 필드는 `schemaVersion`, `transactionId`, `phase`, `previousProfileId`, `targetProfileId`, `startedAt`, `updatedAt`으로 제한해야 한다.
- 토큰, 전체 인증 JSON, 쿠키, 실제 이메일을 넣으면 안 된다.
- 저널과 registry는 같은 디렉터리의 `0600` 임시 파일에 완전히 쓰고 file `fsync` → atomic rename → parent directory `fsync` 순으로 지속해야 한다.
- 각 phase 기록은 그 phase가 보호하는 다음 side effect보다 먼저 디스크에 지속돼야 한다.
- 성공 시 registry 커밋을 먼저 지속한 뒤 journal unlink와 parent directory `fsync`를 완료해야 한다.
- active auth 변경 전 취소·차단은 journal을 unlink하고 parent directory `fsync`까지 완료해 안전 취소해야 한다.
- 잘리거나 schema가 잘못된 저널은 자동 추정하지 않고 STOP해야 한다.
- helper 시작 시 미완료 저널을 감지해 완료 상태를 판정하고 안전한 롤백을 수행해야 한다.
- 메뉴바는 첫 상태 조회와 mutation 실패 뒤 자동 복구를 profile·recovery 조회보다 먼저 시도해야 한다. 시작 복구는 공식 앱을 자동 실행하지 않아야 한다.
- CLI `recovery status`는 일반 auth/registry 복구를 시작하지 않아야 한다. 이미 검증된 finalization evidence 정리만 멱등 재개할 수 있다.

### FR-08 원자 교체

- 대상 JSON을 쓰기 전에 구문과 필수 구조를 검증해야 한다.
- 동일 파일시스템 임시 파일에 쓰고 권한을 `0600`으로 설정해야 한다.
- 파일 내용을 검증한 뒤 rename으로 교체해야 한다.
- 부분 파일이 `auth.json`으로 노출되면 안 된다.

### FR-09 성공 커밋

- 일반 전환은 대상 앱 실행과 이메일 일치 검증이 끝난 후에만 활성 프로필을 갱신해야 한다.
- 검증 전에는 성공 UI를 표시하거나 저널을 지우면 안 된다.

### FR-10 자동 롤백

- target verifier가 typed `target-unverified`를 반환하면 이전 인증과 이전 활성 프로필을 자동 복구해야 한다. process·registry race, verifier 종료 미확인, 내구성 상태 불명확은 쓰지 않고 STOP해야 한다.
- 실행 중 일반 전환의 복원은 이전 이메일 검증 성공 후에만 공식 앱을 재실행해야 한다. 시작 자동 복구는 앱을 재실행하지 않아야 한다.
- 복원 실패 시 앱을 닫아 두고 Keychain 원본과 저널을 보존해야 한다.

### FR-11 만료·취소된 대상 인증

- 인증 실패 시 프로필을 자동 삭제하면 안 된다.
- 명시적 만료·취소 응답이면 `재로그인 필요` 상태를 표시하고 이전 프로필로 롤백해야 한다.
- 네트워크·서버 오류만으로 token이 만료·취소됐다고 단정하면 안 된다.
- 비활성 재로그인 대상은 사용자가 공식 앱 로그인을 완료하고 모든 관련 프로세스를 종료한 뒤 exact profile ID 확인으로만 반영해야 한다.
- exact 대상 identity·refresh·credential 저장·marker 해제를 검증한 뒤 해당 대상을 즉시 active로 커밋해야 한다. 성공 뒤 앱은 자동 실행하지 않아야 한다.
- 재로그인 결과가 pending·blocked이거나 내구 상태와 불일치하면 자동 재시도 없이 STOP해야 한다.

### FR-12 공용 상태 보존

- `auth.json` 외 `~/.codex` 파일을 계정별로 복제하거나 교체하면 안 된다.
- Electron/Chromium 상태를 삭제, 수정, 계정별 복제하면 안 된다.
- 공식 앱 번들을 수정하면 안 된다.

### FR-13 전환 영향 범위

- 전환은 이 Mac의 기본 Codex 인증을 바꾼다.
- 공식 앱뿐 아니라 전환 후 시작되는 새 CLI 세션도 대상 계정을 사용한다.
- 실행 중이던 CLI 세션의 안전한 지속을 보장하지 않으며, 그래서 전환을 차단한다.

### FR-14 진단 로그

- 시각, Codex 버전·build, 전환 단계, 마스킹 이메일, 오류, 필요 시 PID와 안전한 작업 경로만 기록해야 한다.
- 토큰, 전체 `auth.json`, 쿠키, authorization header, 원시 command line을 기록하면 안 된다.
- 파일 해시가 필요하면 인증 내용 복원에 사용할 수 없는 SHA-256만 기록한다.

### FR-15 사용량 분리

- MVP는 사용량을 전환 성공 판정에 사용하지 않아야 한다.
- `account/rateLimits/read` 기반 사용량 표시는 후속 읽기 전용 기능이어야 한다.
- 조회 실패가 프로필 삭제, 전환 실패, 자동 계정 선택을 유발하면 안 된다.

### FR-16 로컬 프로필 삭제

- 삭제는 exact inactive profile ID에만 허용해야 한다. 활성 프로필은 UI에서 숨기고 Core에서도 거부해야 한다.
- 해당 Keychain item과 registry profile만 삭제하고 현재 `auth.json`, active profile, OpenAI 계정은 변경하지 않아야 한다.
- secret-free 삭제 marker를 side effect 전에 내구 기록하고 Keychain→registry→marker 순서로 멱등 완료해야 한다.
- Keychain 거부나 crash 뒤 marker와 registry를 보존하고 다음 자동 복구에서 재개해야 한다.
- 삭제 marker와 switch journal이 공존하거나 expected active가 달라지면 자동 추정·삭제 없이 STOP해야 한다.

## 11. Spike 검증 계획과 완료 조건

### 11.1 테스트 데이터

- 별도 ChatGPT 로그인인 계정 A와 B를 사용한다.
- 같은 로그인 내 workspace 전환 테스트가 아니다.
- 민감한 회사 코드, 문서, 고객 데이터 없이 만든 전용 테스트 task를 사용한다.

### 11.2 핵심 왕복 시나리오

먼저 A에서 비민감 전용 task를 **한 번만** 만들고 실제 메시지를 성공시켜 기준 task ID를 고정한다. 그 뒤 같은 ID에서 다음 왕복을 수행한다.

1. helper core로 B로 전환한다.
2. `account/read` 이메일이 B와 일치함을 확인한다.
3. 기준 task를 열고 B에서 새 실제 메시지를 성공시킨다.
4. helper core로 A로 복귀한다.
5. `account/read` 이메일이 A와 일치함을 확인한다.
6. 같은 기준 task에서 A의 새 실제 메시지를 성공시킨다.
7. 앱 종료 후 `auth.json`이 마지막 대상 계정으로 유지되는지 확인한다.

이 왕복을 **동일한 기준 task ID로** 3회 연속 성공해야 한다. 각 회차마다 새 task를 만들면 안 된다. 단순 화면 열림, task 목록 표시, 이메일 표시만으로는 통과가 아니다.

### 11.3 추가 필수 시나리오

- 전환 전 현재 인증 최신화 후 재로그인 없이 복귀
- 앱 종료 중 인증 변경 발생 여부 확인
- 독립 CLI 실행 중 전환 차단
- 잘못된 JSON, 빈 파일, 일부 파일, 이메일 불일치 대상의 사전 거부
- 대상 인증 만료 시 이전 계정 롤백
- 대상 앱 실행 실패 시 이전 계정 롤백
- 롤백 실패 모의 시 앱 미실행과 복구 정보 보존
- 전환 중 프로세스 중단 후 저널 기반 다음 실행 복구
- helper 밖 `codex login`으로 미등록 이메일이 생겼을 때 명시적 선택 요구
- Codex 재실행·종료 후 이전 인증으로 되돌아가지 않음

### 11.4 Spike 판정

**PASS**

- 핵심 왕복 3회 연속 성공
- 각 구간에서 이메일 검증과 실제 메시지 성공
- 필수 안전·롤백 시나리오 성공
- 인증 파일이 이전 계정으로 되돌아가지 않음
- 새 로그인 없이 양방향 복귀 가능

**NO-GO — 제품 가설의 구조적 실패**

- 올바른 A/B 인증 전환이 확인됐는데도 같은 task ID가 계정 ownership 경계 때문에 B에서 열리지 않거나 실제 요청이 거부됨
- A 복귀 후 같은 ID의 단일 history가 이어지지 않음
- task copy, fork, import 또는 새 ID가 있어야만 진행 가능함

이 경우 메뉴바 제품 구현을 중단한다. task 복사, 요약 이관, 새 task 생성으로 성공 기준을 우회하지 않는다.

**FIX-AND-RETEST — Helper 구현·환경 실패**

- 이메일 verifier, process 분류, 정상 종료 대기, launch orchestration, 원자 writer, recovery, 로그 마스킹 결함
- UI 이메일과 active auth 불일치 또는 이전 프로세스의 덮어쓰기가 Helper 결함으로 재현됨
- 일시적 network 실패

결함을 수정해 Unit/Integration을 통과한 뒤 기준 task 생성부터 전체 3-cycle을 새로 실행한다. 이 상태에서는 아직 메뉴바 제품 구현을 시작하지 않지만 제품 가설을 NO-GO로 판정하지도 않는다.

**STOP/INCONCLUSIVE — 안전하거나 객관적인 판정 불가**

- 이메일, task ID 또는 실제 요청 계정을 신뢰성 있게 입증하지 못함
- rollback source 검증 실패, 관련 process 잔존, malformed journal, 핵심 호환성 계약 변경

원인을 해결하기 전 auth 변경과 Spike를 중단한다. 증거 부족을 PASS나 구조적 NO-GO로 바꾸지 않는다.

**개발 GO — 증거 형식 공백 수용**

2026-07-30 사용자 확인상 동일 task의 A↔B 기능 왕복 3회와 메시지 응답이 완료됐고 B-011 자동 롤백을 확인했다. cycle nonce와 단계별 task ID 기록은 보존하지 않았으므로 B-010 정식 PASS는 아니다. ADR-027에 따라 사용자가 이 공백을 수용해 메뉴바 MVP 개발을 승인했으며, 정식 증거는 MVP 완료·배포 전에 확보한다.

## 12. 단계별 산출물

### 단계 1: 문서와 Swift CLI core

- 전환 상태 머신과 실패 지점 명세
- 재사용 가능한 Swift package/core
- 진단, 등록, 전환, 검증, 복원 명령
- unit test와 임시 경로 통합 test
- 실제 공식 앱을 이용한 수동 Spike 절차
- 비밀 없는 구조화 결과와 최종 판정 리포트

### 단계 2: 메뉴바 MVP

- CLI core를 호출하는 `MenuBarExtra` 앱
- 최대 3개 프로필 등록·표시·전환
- Keychain 저장
- 전환 확인, 진행, 오류, 재로그인 UI
- 비활성 프로필 삭제·재등록 UI
- 시작 시 저널 복구
- 개인 배포용 GitHub 저장소와 설치 지침

### 단계 3: 후속 기능

- 프로필 4개 이상
- 앱 내부 격리 로그인
- 사용량 표시
- Developer ID 서명·공증

## 13. MVP 완료 조건

다음을 모두 만족해야 MVP 완료다.

- `07_test_acceptance.md`의 Spike GO 조건을 모두 충족함
- 최대 3개 프로필 등록 가능, 네 번째 등록은 무변경 거부
- 추가 등록 후 새 계정 활성 유지와 이전 저장본 무변경 성공
- 앱 실행·종료 상태 모두에서 수동 전환 성공
- 이미 활성인 카드 선택 시 무변경 동작
- 독립 CLI 감지 시 무변경 차단
- 비활성 프로필 인증은 Keychain에만 저장되고 활성 인증 한 개만 `~/.codex/auth.json`에 존재함
- 원자 교체, lock, 저널, 자동 롤백 검증
- 만료 토큰과 미등록 외부 로그인 처리 검증
- `needsRelogin` 비활성 대상의 exact-ID 재로그인 반영, 대상 즉시 활성화, 앱 수동 실행 검증
- 비활성 프로필의 Keychain·registry 삭제, 활성 로그인 불변, 같은 계정 재등록 검증
- Codex 버전 변경 사전 검사
- 실제 task 왕복 성공 기준 유지
- 로그·테스트 산출물에서 인증 비밀 미검출

## 14. 배포와 운영

- 초기 배포는 개인 사용 및 GitHub 공개 배포다.
- App Store sandbox는 목표가 아니다. 기본 `~/.codex`, 프로세스 제어, Keychain 접근이 제품 동작에 필요하다.
- 안정화 후 Developer ID 서명과 공증을 추가한다.
- 공식 Codex 업데이트 이후 첫 전환은 호환성 검사 결과를 사용자에게 보여준다.
- 제품이 보안 격리를 제공하지 않는다는 경고를 첫 실행과 설정 화면에 명시한다.
